## 📋 Overview

This update implements a **major architectural change** to the profit recognition system, moving from "Income Split" to "Profit on Expense" logic. We also introduce **Work Orders (Cost Items)** for granular project tracking.

---

## 🔄 Key Changes Summary

### 1. **Database Schema Updates** ✅ COMPLETE

#### New Model: `ProjectCostItem`
- Tracks specific agreed work items (e.g., "Ceramic 100m²")
- Links transactions to specific cost items instead of generic categories
- Fields: name, quantity, unit, unitPrice, estimatedTotal, totalPaid, status

#### Updated Models:
- **Project**: Added `projectSafeBalance` field
- **Transaction**: Added `projectCostItemId` field, `transactionDate` is now editable
- **Tenant**: Added `projectCostItems` relation

### 2. **Business Logic Refactor** ✅ COMPLETE

#### OLD LOGIC (DISCARDED):
```
Income 100k → 80k Project Safe / 20k Office Revenue
```

#### NEW LOGIC (IMPLEMENTED):

**A. INCOME Transaction:**
- Add **full amount** to `Project.projectSafeBalance`
- Profit = 0 (not recognized yet)

**B. EXPENSE Transaction (Direct/Service):**
- Deduct amount from `Project.projectSafeBalance`
- Calculate Profit = `Amount × (ManagementFeePercent / 100)`
- Transfer profit from `projectSafeBalance` to `officeRevenue`

**C. EXPENSE Transaction (Inventory Purchase):**
- Deduct amount from `Project.projectSafeBalance`
- Profit = 0 (deferred until usage)
- Create `MaterialBatch` record

**D. INVENTORY USAGE:**
- Calculate Profit = `ValueConsumed × (ManagementFeePercent / 100)`
- Transfer profit from `projectSafeBalance` to `officeRevenue`

### 3. **API Updates** ✅ COMPLETE

#### New Endpoints:

**Project Cost Items:**
- `POST /api/project-cost-items` - Create work order
- `GET /api/project-cost-items/project/:projectId` - Get all items for project
- `GET /api/project-cost-items/:id` - Get single item
- `PUT /api/project-cost-items/:id` - Update item
- `DELETE /api/project-cost-items/:id` - Delete item (Admin only)

**Transactions V1.2:**
- `POST /api/transactions/v2` - Create transaction with new profit logic
- `POST /api/transactions/inventory-usage` - Record material usage with profit
- `GET /api/transactions/projects/:id/inventory` - Get project inventory

#### Updated Endpoints:
- `POST /api/transactions` - Now accepts:
  - `projectCostItemId` (optional)
  - `transactionDate` (optional, defaults to now)
  - `payerUserId` (for managers to assign payer)

## 🗄️ Database Migration

### Step 1: Run Prisma Migration

```bash
cd server
npx prisma migrate dev --name v1_2_profit_on_expense
```

This will:
- Create `project_cost_items` table
- Add `projectSafeBalance` to `projects` table
- Add `projectCostItemId` to `transactions` table
- Update indexes

### Step 2: Data Migration (Optional)

If you have existing projects, you may want to initialize `projectSafeBalance`:

```sql
-- Initialize projectSafeBalance from operationalFund
UPDATE projects 
SET "projectSafeBalance" = "operationalFund"
WHERE "projectSafeBalance" = 0;
```

#### A. Grouping Transactions by Cost Item
```jsx
const groupedTransactions = transactions.reduce((acc, tx) => {
  const itemId = tx.projectCostItemId || 'uncategorized';
  if (!acc[itemId]) {
    acc[itemId] = {
      costItem: tx.projectCostItem,
      transactions: []
    };
  }
  acc[itemId].transactions.push(tx);
  return acc;
}, {});
```

## 🚨 Breaking Changes

### For Existing Code:

1. **Income Transactions:** No longer split automatically. Full amount goes to `projectSafeBalance`.
2. **Profit Recognition:** Now happens on expense, not income.
3. **Transaction Creation:** Use `/api/transactions/v2` for new logic, or update existing endpoint.

### Migration Path:

- **Option A:** Use `/api/transactions/v2` for all new transactions
- **Option B:** Update existing `/api/transactions` endpoint to use V1.2 logic
- **Recommended:** Option A for gradual migration, then deprecate old endpoint

---

## 📝 Notes for Frontend Team

1. **Project Safe Balance** is the new "source of truth" for project cash.
2. **Office Revenue** now accumulates from expense profits, not income splits.
3. **Cost Items** are optional but recommended for better tracking.
4. **Arabic Categories** should be used in all dropdowns (use the constants file).
5. **Notifications** will be sent when `projectSafeBalance < 0`.
